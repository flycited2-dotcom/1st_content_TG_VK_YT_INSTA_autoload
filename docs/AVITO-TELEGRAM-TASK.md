## Реализация и критерии готовности

1. Инвентаризировать свежую партию. Для каждого поста хранить source id/SKU/series, категорию, путь/URL именно готовой карточки, источник УТП, конечную цену/валюту, timestamp/hash источников. Исключать чужие категории, без цены, без соответствующего изображения и сомнительные соответствия. Предоставить сводку причин пропуска.
2. Сделать повторяемый импорт готовых карточек и текстов в существующую очередь подтверждения. Сначала dry-run без Telegram/изменений production state, затем явный режим отправки только в review. Никакой прямой публикации, клика approve, отключения confirm или массового удаления старой очереди.
3. Сохранить оригинальные изображения. Проверять корректный тип изображения и безопасные пути; использовать абсолютные стабильные серверные пути, доступные работающему боту при последующем approve. Не подставлять фото поставщика, выдавая его за сгенерированную карточку.
4. Содержательная подпись: модель/серия, исходное УТП, подтверждённые выгоды/характеристики, продажная цена (у серии «от»), правдивый CTA. Учитывать лимит Telegram и HTML escaping; длинные описания сокращать по смысловым блокам. Нельзя молча обрезать число/единицу или цену.
5. Дедупликация и возобновление: повторный запуск не отправляет снова pending/published/rejected без явного запроса. При ошибке/таймауте не помечать как доставленное. Не допускать повторной отправки при конкурентных запусках; неоднозначные таймауты требуют сверки. Retry-after соблюдать, отправлять с ограничением темпа. По результату нужны реальные review message_id, а не только локальный статус.
6. Использовать существующий approve/reject и общую БД работающего cf-bot. Проверить права владельца в существующем обработчике; не расширять список лиц, которым разрешено подтверждение.
7. Минимальные необходимые тесты: категории; конечные цены без повторной наценки и «от»; соответствие карточек; HTML/длина подписи; повторный запуск; review == publish channel запрещён; ошибка Telegram/429; отказ от обхода подтверждения. Запустить тесты и записать фактический вывод.
8. Документировать запуск, dry-run, безопасную доставку новых готовых карточек, проверки и откат. Постоянный импорт должен использовать существующий worker/timer только после проверки; не менять nginx/systemd и не развёртывать без сверки владельцем задачи.
