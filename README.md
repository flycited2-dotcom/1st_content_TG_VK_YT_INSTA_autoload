# Контент-завод (Content Factory)

> Главный репозиторий омниканального проекта Telegram / VK / Instagram / YouTube.
> Текущий рабочий этап — полуавтоматический товарный контент со строгим ревью.
> Общая последовательность развития: [docs/OMNICHANNEL-ROADMAP.md](docs/OMNICHANNEL-ROADMAP.md).
> Согласованный стандарт карточек стабилизаторов: [docs/CARD-STYLE-STABILIZERS.md](docs/CARD-STYLE-STABILIZERS.md).
> Обязательная точность товара и поиск отсутствующих фото: [docs/PRODUCT-IMAGE-FIDELITY.md](docs/PRODUCT-IMAGE-FIDELITY.md).

Автоматический конвейер: **берёт товары из БД → считает цену → пишет краткое описание →
генерирует карточку-картинку (фотоагент) → проверяет правилами → публикует в Telegram-канал**.
Полностью по расписанию/задачам, без ручной возни.

> Это **новый проект**, но не с нуля: «движок» (источник данных, мост к фотоагенту, очередь,
> авто-побудка агента, генерация описаний, режимы карточек, авто-ретрай) **уже построен и обкатан**
> в проекте `avito-bridge` (публикация кондиционеров на Avito). Здесь мы **переиспользуем этот движок**,
> убираем Avito-специфику (XML-фид) и заменяем публикацию на **Telegram-канал**.

## Цель (словами владельца)
Есть «обсервер-агент» (оркестратор), которому ставят задачу: «возьми сегодня 10 карточек из
*<категория>*, сгенерируй краткое описание, отправь в фотоагент, получи карточку, проверь точность,
опубликуй в моём Telegram-канале — завтра в 10:00 и 14:00». Задачи ставятся на день/неделю вперёд,
дальше всё крутится само. Потом владелец добавляет товары/поставщиков/категории — без переписывания.

## Ключевые решения (согласованы с владельцем)
1. **Публикация:** Telegram **Bot API**, бот — администратор канала (`sendPhoto` + подпись). Бот и права уже есть.
2. **Ревизия (точность):** **детерминированные правила, без LLM** (цена>0, ТТХ на месте, карточка
   сгенерирована, описание непустое/без стоп-слов). Не прошло — не публикуем, помечаем.
3. **Постановка задач:** основной путь — **команды боту в Telegram**; плюс поддержать **файлы-планы YAML**
   (оба способа кладут задачи в одну очередь, исполняет планировщик).
4. Контент-движок и описания — **без LLM-ключа** (как в avito-bridge): копирайт детерминированный/шаблонный
   с вариативностью + ручные тексты-переопределения. (LLM можно подключить позже как опцию.)

## Пилот
Первый прогон — на **остатках кондиционеров** (та же БД `oasis`), но публикуем **в Telegram, не в Avito**.
Это даёт рабочий «контент-завод» end-to-end; дальше владелец расширяет категории/поставщиков.

## Авторизация VK ID

Приложение VK ID пилота: `54732587`. Серверный OAuth 2.1/PKCE хранит короткий
access token и refresh token только в игнорируемом `state/vk-tokens.json`.
Новые пользовательские Access token получают через OAuth VK ID. Контент-завод
запрашивает `vkid.personal_info offline wall photos groups` в защищённом PKCE-потоке.
VK может вернуть только базовые права, если расширенные `wall/photos/groups` ещё не
согласованы для приложения; фактический `scope` обязательно проверяется после обмена.

```powershell
python -m content_factory.publish.vk_oauth start
python -m content_factory.publish.vk_oauth exchange --callback-url "URL_ПОСЛЕ_АВТОРИЗАЦИИ"
python -m content_factory.publish.vk_oauth refresh
```

Для публикации нужен отдельный пользовательский токен Standalone-приложения либо
токен сообщества с подходящими методами. Токены, callback URL с кодом и содержимое
`state/` запрещено добавлять в Git или чат.

Проверка ключа сообщества `241020718` через VK API `5.199` показала: права `wall`
и `photos` у ключа отображаются, но `photos.getWallUploadServer` возвращает ошибку
`27 Group authorization failed`. Загрузка через канал фотографий сообщений также
не подходит: `wall.post` принимает запрос и создаёт запись, но VK молча удаляет такое
вложение со стены. Контрольная запись `wall-241020718_1` поэтому получилась без фото.
Издатель теперь останавливает подобную операцию заранее и не создаёт неполный пост.

Текущий ключ сообщества остаётся рабочим для управления доступными методами сообщества:
через `groups.edit` уже заполнены публичные описание, сайт и телефон. Он также пригоден
для текстовых записей, сообщений, Callback/Long Poll и поддерживаемых разделов. Однако
тип существующего ключа нельзя «доделать» до пользовательского: нативная загрузка фото
на стену требует отдельной пользовательской авторизации через OAuth VK ID с фактически
выданными правами `wall` и `photos`. `dry_run: true` остаётся защитным значением по
умолчанию.

Для закрытого полуавтоматического пилота используется поддерживаемый VK Share:
завод формирует текст, публикует утверждённую карточку по HTTPS и создаёт ссылку
`https://vk.com/share.php`. Владелец вручную подтверждает финальную публикацию.

Целевая площадка пилота — бизнес-сообщество `vk.ru/club241020718`. В конфигурации его
стена записана как `owner_id: -241020718`; отрицательный идентификатор отличает сообщество
от личной страницы. `dry_run: true` остаётся включённым до получения отдельного токена
издателя с правами сообщества и контрольной публикации.

### Переходный VK-мост с ручным добавлением фото

Пока VK не выдал пользовательскому приложению право нативно загружать фотографии,
разрешён отдельный ограниченный поток: один уже прошедший Telegram-публикацию климатический
материал превращается в текстовую запись сообщества, а готовую карточку владелец прикрепляет
через редактирование записи. Это не подмена штатного `publish`: мост вызывается отдельной
командой, пропускает `sold`/«ПРОДАНО», проверяет наличие файла карточки и хранит собственный
антидубль в SQLite.

```bash
# безопасный просмотр кандидата, без публикации
python -m content_factory.publish.vk_text_sync

# один реальный пост; второй за этот запуск никогда не отправляется
python -m content_factory.publish.vk_text_sync --publish
```

Прод-таймер `cf-vk-text.timer` запускает мост раз в сутки в 10:15 с небольшим случайным
смещением. Источник `/opt/content-factory/state/content_factory.db` открывается только для
чтения; состояние VK хранится отдельно в `/opt/content-factory-vk/state/vk-sync.db`.

### VK Content Planner v1

Планировщик `content_factory.orchestrator.vk_content_plan` формирует очередь на 14 дней
(понедельник–суббота, один пост в день), чередует категории и бренды и использует только
уже прошедшие Telegram-review материалы с повторно проверенной ценой и наличием. Состояние
хранится в `/opt/content-factory-vk/state/vk-plan.db`.

```bash
# dry-run: сформировать план, но ничего не отправлять
python -m content_factory.orchestrator.vk_content_plan

# L1: отправлять по одному материалу на ревью и после одобрения создавать отложенный текст
VK_PLAN_PUBLISH=1 python -m content_factory.orchestrator.vk_content_plan
```

В Telegram владелец нажимает «Одобрить для VK» или «Пропустить». После одобрения завод
создаёт отложенную текстовую запись и просит вручную прикрепить готовую карточку. За три
часа до выхода неподтверждённого фото приходит повторное предупреждение. Повторные запуски
идемпотентны и не создают второй материал из того же источника. `cf-vk-plan.timer` запускает
цикл каждые 30 минут; без `VK_PLAN_PUBLISH=1` он остаётся безопасным dry-run.

Редакционный контур этапа 2 находится в `content_factory.agents.editorial`. Он выбирает
полезную тему, собирает разрешённые факты из `config/vk-editorial-sources.yaml`, формирует
отдельный VK-текст и пропускает его через строгого критика. Технический тезис не может
появиться без связанного официального источника; исследовательский пакет и вердикт
сохраняются в таблице `vk_editorial_audit`. Политика и общественные новости заблокированы.
Пока VK не выдал загрузку фото, редакционные материалы планируются как текстовые записи;
товарные публикации продолжают требовать ручного подтверждения фотографии.

`content_factory.storefront.vk_catalog` готовит управляемую витрину из 15–30 опорных
товаров. В неё проходят только доступные позиции с повторно проверенной ценой, готовой
квадратной первой фотографией и персональной ссылкой заявки в Telegram. Ежедневный
`cf-vk-storefront.timer` обновляет JSON-манифест и помечает исчезнувшие позиции
неактивными. Сам манифест не является обходом VK API и не загружает товары в сообщество:
нативная синхронизация включается после получения права на фотографии.
